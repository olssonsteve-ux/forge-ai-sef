# PRR-0001 - v0.4.0 Post-Release Review

## Status

PASS WITH COMMENTS.

## Release Summary

Forge `v0.4.0` released the first Governance Runtime implementation: the read-only Status Service and `forge status` command.

The release included:

- Capability Slice standard
- Capability Slice template
- CS-002.1 Governance Runtime Status Service
- DAR-CS-0001 slice review
- EB-002.1 implementation brief
- read-only Status Service implementation
- `forge status` CLI command
- tests for status categories, missing governance artifacts, no-Git repositories, CLI execution, and read-only behavior

The release tag `v0.4.0` points to commit `c4d510f1d00c887ee7b8fea3a259514ad83ae80c`.

## What Went Well

- The release followed the Forge hierarchy: FCS, Capability Slice, DAR, Engineering Brief, implementation, implementation review, release.
- `forge status` stayed inside the read-only boundary.
- Tests, lint, format checks, `forge status`, and `git diff --check` passed before release.
- The release tag was pushed successfully.
- Post-release verification found the documentation version inconsistency quickly.

## What Went Wrong

After the `v0.4.0` tag was created, documentation still referenced Forge `0.3.3` in active project state and handoff documents.

The inconsistency appeared in:

- `README.md`
- `PROJECT_STATE.md`
- `AI_HANDOFF.md`

The changelog also needed an explicit `0.4.0` section instead of leaving the released work under `Unreleased`.

## Version Inconsistency Detected After Release

The repository was functionally released as `v0.4.0`, but some documentation still described the repository as being at Forge `0.3.3`.

This created a traceability mismatch between:

- Git tag
- README current state
- project memory
- AI handoff context
- changelog release status

The issue was corrected in commit `7487eaf9d8efcdbfeddcb2a78b5b92124f048fb4`.

## Root Cause

Forge had release documentation and release commands, but no explicit release-time version consistency gate.

The release process verified implementation quality and Git tag correctness, but it did not require a systematic check that active documentation matched the release tag.

The root cause was a governance gap, not a code defect.

## Why CI Did Not Catch It

CI currently runs:

- tests
- Ruff lint checks
- Ruff format checks

These checks validate Python behavior and formatting. They do not understand Forge release state, Git tags, changelog sections, project memory, or documentation version references.

CI did exactly what it was configured to do. It was not configured to detect release metadata drift.

## Why `forge status` Did Not Catch It

`forge status` in `v0.4.0` checks artifact presence and simple repository status. It does not inspect semantic consistency between:

- current Git tag
- package version
- README current state
- `PROJECT_STATE.md`
- `AI_HANDOFF.md`
- `CHANGELOG.md`
- release documentation

This is expected behavior for CS-002.1. Version consistency was not part of the first Status Service slice, and adding it implicitly would have expanded scope beyond EB-002.1.

## Recommended Future Improvement

Forge should define an explicit Governance Runtime capability slice for version consistency.

The check should evaluate whether release-facing documents agree on the current release identity before and after tagging.

Initial targets should include:

- Git tag
- `pyproject.toml`
- `README.md`
- `PROJECT_STATE.md`
- `AI_HANDOFF.md`
- `CHANGELOG.md`
- release checklist
- generated project template metadata when relevant

The check should remain read-only unless a future accepted slice authorizes suggested fixes or controlled updates.

## Proposed Future Capability Slice

Proposed slice:

```text
CS-002.2-Governance-Runtime-Version-Consistency-Check.md
```

Purpose:

Define a read-only Governance Runtime check that detects version drift across release metadata, project memory, documentation, package metadata, and Git tags.

Initial scope:

- detect stale version references in active release-facing documentation
- detect missing changelog release section
- detect mismatch between current release tag and project state
- detect mismatch between package metadata and release documentation when package metadata is expected to reflect the release
- report findings without modifying files

Non-goals:

- automatic version bumping
- automatic changelog rewriting
- automatic Git tagging
- release approval
- package publishing
- mutation of project memory

Suggested future command surface:

```text
forge status
```

Version consistency should first appear as an additional Governance Runtime status category or status item, not as a separate command.

## Should This Become Part Of Governance Runtime?

Yes.

Version consistency is a governance concern because release identity links code, documentation, project memory, tags, and handoff context.

It should become part of Governance Runtime after a dedicated Capability Slice and Engineering Brief are accepted. It should not be retrofitted into CS-002.1 because that slice intentionally covered artifact presence and simple status only.

## Decision

PASS WITH COMMENTS.

Forge `v0.4.0` is valid, but the post-release inconsistency shows that Forge needs an explicit version consistency check before release confidence can be considered mature.
