# EB-002.2 - Implement Governance Runtime Version Consistency Check

Status: Accepted for implementation planning

Date: 2026-07-09

## Purpose

Implement the read-only Governance Runtime Version Consistency Check defined by CS-002.2.

The check extends `forge status` by adding one additional Status category that reports whether active release-facing version information agrees across the repository.

This brief exists to prevent the version drift discovered after the `v0.4.0` release from recurring unnoticed.

## Relationship To FCS-002

FCS-002 defines Governance Runtime as the operational layer that evaluates governance state, release readiness evidence, project memory health, repository health, risk, and documentation completeness.

Version consistency is a Governance Runtime signal because release identity crosses Git tags, documentation, changelog, project memory, package metadata, and handoff context.

## Status Service Integration

The existing Status Service should add one category:

```text
Version Consistency Status
```

The category should use the existing `StatusCategory`, `StatusItem`, `StatusReport`, and `StatusState` model unless implementation shows a clear need for a small helper structure.

The category should be generated by `evaluate_status()` alongside existing categories.

The CLI should continue to call the Status Service and render the full report. `forge status` should remain the only command surface.

## Version Detection Approach

The implementation should detect version references conservatively.

Supported version form:

```text
vMAJOR.MINOR.PATCH
MAJOR.MINOR.PATCH
```

Examples:

- `v0.4.0`
- `0.4.0`

Initial target version:

- prefer the latest local Git tag matching `vN.N.N`
- if no matching tag exists, report Git tag status as `MISSING` or `NOT_APPLICABLE`

Active document version sources:

- README current state
- `PROJECT_STATE.md` current version
- AI handoff current repository state
- latest matching changelog release heading
- `pyproject.toml` project version when present

Historical references:

- changelog sections for older versions
- review documents
- release checklists for prior releases
- architecture decisions that mention past versions
- post-release reviews that explain historical incidents

Historical references must not be treated as mismatches by default.

## Git Interaction

Allowed Git interaction:

- read local tags
- inspect current working tree state
- avoid network calls

Recommended Git commands:

```text
git tag --list v*
git status --porcelain
```

Git failures should produce status findings, not unhandled errors.

The implementation must not:

- create tags
- delete tags
- push tags
- commit
- stage files
- fetch remote refs
- compare remote tags

## Documentation Parsing Strategy

Parsing should be simple, conservative, and file-specific.

Recommended active reference rules:

- `README.md`: inspect the Current State section or first release/version statement.
- `PROJECT_STATE.md`: inspect the Current Version section.
- `AI_HANDOFF.md`: inspect the Current Repository State section.
- `CHANGELOG.md`: inspect release headings and require a heading for the latest tag without requiring old sections to match.
- `pyproject.toml`: inspect `[project].version` if present; treat mismatch as `WARNING`, not failure, until package publishing policy is accepted.
- `docs/release/`: inspect current release documents only when a matching current release checklist exists; historical release checklists are allowed to mention old versions.

The implementation should not scan every document for every version string and treat all differences as drift.

## Error Handling

Invalid execution should follow existing Status Service rules.

Status findings:

- missing Git metadata: `NOT_APPLICABLE` or `WARNING`
- no matching release tag: `MISSING`
- missing README: `MISSING`
- missing CHANGELOG: `MISSING`
- missing PROJECT_STATE: `MISSING`
- missing AI_HANDOFF: `MISSING`
- missing pyproject: `NOT_APPLICABLE`
- unreadable file: `WARNING` or `BLOCKED`
- dirty working tree: `WARNING`
- version mismatch in active source: `WARNING`

Warnings and missing sources should not cause a non-zero exit code.

## CLI Behavior

The implementation extends:

```text
forge status
```

No new CLI command shall be introduced.

No new options are required for the first implementation.

The command should:

- inspect the current repository by default
- include Version Consistency Status in the human-readable output
- perform no file writes
- return exit code `0` when status evaluation completes, even if version warnings are found
- return non-zero only for invalid execution or unexpected internal failure

The output must avoid release approval language.

Allowed wording:

- "Version Consistency Status"
- "Version mismatch"
- "Missing version source"
- "Working tree has uncommitted changes"
- "Recommended next action"

Avoid wording:

- "Approved"
- "Certified"
- "Release passed"
- "Release blocked" unless a future release-gate slice authorizes blocking behavior

## Testing Strategy

Tests should extend `tests/test_status.py`.

Required tests:

- matching versions produce `OK`
- missing README reports `MISSING`
- missing CHANGELOG reports `MISSING`
- missing Git tag reports `MISSING` or `NOT_APPLICABLE`
- multiple active version mismatches report `WARNING`
- clean repository can report clean working tree context when Git metadata is available
- dirty repository reports warning context when Git metadata is available
- historical changelog versions do not fail active consistency
- missing `pyproject.toml` is `NOT_APPLICABLE`
- service remains read-only
- CLI remains read-only
- status category generation includes Version Consistency Status

Fixture guidance:

- Use temporary repositories for Git tag and dirty working tree cases.
- Keep fixtures small and explicit.
- Prefer writing only test fixture files.
- Compare file snapshots before and after status evaluation.
