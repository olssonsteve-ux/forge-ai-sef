# EB-002.1 - Implement Governance Runtime Status Service

Status: Accepted for implementation planning

Date: 2026-07-08

## Purpose

Implement the first Governance Runtime service defined by CS-002.1: a read-only Status Service that inspects a repository and reports its Forge governance and engineering status.

This Engineering Brief authorizes implementation planning for the future command:

```text
forge status
```

It does not authorize review scoring, release approval, project memory mutation, policy packs, persisted reports, or any automatic remediation.

## Governing Inputs

Implementation must follow:

- `CONSTITUTION.md`
- `AI_ENGINEERING_CONDUCT.md`
- `docs/capabilities/FCS-002-Governance-Runtime.md`
- `docs/capabilities/CS-002.1-Governance-Runtime-Status-Service.md`

## Implementation Scope

In scope:

- add a read-only internal Status Service
- add a `forge status` CLI command
- inspect a target repository path
- default to the current working directory
- report status across the CS-002.1 categories
- detect expected Forge governance artifacts
- detect tests, CI, release documentation, capabilities, slices, Engineering Briefs, and ADRs
- inspect Git availability and working tree state when possible
- provide human-readable output
- return non-zero exit codes only for invalid command execution
- add tests for service behavior and CLI behavior
- update user-facing documentation after implementation

Out of scope:

- writing, editing, creating, or deleting project files at runtime
- updating `PROJECT_STATE.md`, `PROJECT_BRAIN.md`, `AI_HANDOFF.md`, or any project memory file at runtime
- persisted status reports
- JSON output
- Governance Score
- code-quality scoring
- release approval
- release blocking
- review creation
- ADR creation
- policy packs
- strict mode enforcement
- automatic recommendations that change files
- `forge review`
- `forge doctor`
- `forge release`

## Architecture Approach

Use a small internal service module with a CLI adapter.

The service should contain repository inspection and result generation logic. The CLI should only parse command options, call the service, render the human-readable output, and choose the process exit code.

Recommended structure:

- `forge/status.py` owns status categories, result states, repository inspection, Git inspection, and human-readable status data.
- `forge/cli.py` wires `forge status` into the existing Typer application.
- `tests/test_status.py` verifies service behavior and CLI behavior.

The first implementation should avoid a large framework. Simple data structures are preferred until status output proves it needs stronger modeling.

## Service Boundaries

The Status Service may:

- read filesystem metadata
- read directory existence
- read file existence
- inspect Git metadata through safe read-only commands or filesystem checks
- produce status results
- produce warnings and recommendations

The Status Service must not:

- write files
- create directories
- stage Git changes
- commit changes
- update project memory
- persist reports
- modify configuration
- install dependencies
- call network services

The implementation should make the read-only boundary testable.

## Status Categories

The implementation must report these categories from CS-002.1:

- Constitutional Status
- Governance Status
- Documentation Status
- Capability Status
- Engineering Workflow Status
- Testing Status
- Release Status
- Runtime Memory Status
- Repository Status

Each category should include:

- category name
- result state
- concise message
- optional details
- optional recommended next action

## Result States

Use only the CS-002.1 result states:

- `OK`
- `WARNING`
- `MISSING`
- `BLOCKED`
- `NOT_APPLICABLE`

The initial implementation must not calculate an aggregate score.

## Repository Detection Rules

Default target:

- current working directory

Initial repository validity:

- a readable path is required
- a path that is not a directory is invalid execution
- absence of Forge governance files is a status finding, not an execution failure
- missing `CONSTITUTION.md` should report `MISSING`
- missing project memory files should report `MISSING`

The command should not require the target to be a Git repository.

## CLI Behavior

Command:

```text
forge status
```

Initial options:

- no required arguments
- no file output option
- no JSON option
- no strict mode option in the first implementation

Behavior:

- inspect the current working directory
- print human-readable status output
- perform no file writes
- return exit code `0` when status evaluation completes, even if warnings or missing artifacts are found
- return non-zero only for invalid execution, such as unreadable path or unexpected internal failure

Output should avoid implying approval.

Preferred language:

- "Status"
- "Missing"
- "Warning"
- "Recommended next action"

Avoid language such as:

- "Approved"
- "Certified"
- "Release ready"
- "Compliant" unless the evidence and meaning are explicitly bounded

## Error Handling

Invalid execution should produce a clear error message and non-zero exit code.

Examples:

- target path cannot be resolved
- target path is not a directory
- target path cannot be read
- unexpected internal exception

Non-errors:

- missing Constitution
- missing AI Engineering Conduct
- missing project memory
- missing Git repository
- missing CI
- missing tests
- missing release documentation

These are status findings, not command failures.

## Tests Required

Tests must cover:

- complete Forge-like project reports expected categories
- missing `CONSTITUTION.md` reports `MISSING`
- missing `PROJECT_STATE.md` reports `MISSING`
- directory without `.git` still evaluates and exits successfully
- CLI runs without writing files
- service runs without writing files
- result categories are generated consistently
- warnings or missing optional artifacts do not fail the command
- invalid path fails clearly
- Git working tree awareness is reported when Git metadata is available

Read-only tests should compare filesystem state before and after execution for representative fixtures.

## Documentation Updates Required

After implementation, update:

- `README.md` with `forge status` usage
- `CHANGELOG.md` with the new command
- `PROJECT_STATE.md` with implementation status
- `PROJECT_BRAIN.md` with durable implementation decisions
- `AI_HANDOFF.md` with future-agent guidance for Status Service maintenance

Documentation must state that `forge status` is informational and does not approve releases or mutate project memory.

## Acceptance Criteria

EB-002.1 implementation is complete when:

- `forge status` exists
- `forge status` inspects the current working directory by default
- Status Service logic is separated from CLI wiring
- output includes the required CS-002.1 status categories
- result states use only `OK`, `WARNING`, `MISSING`, `BLOCKED`, and `NOT_APPLICABLE`
- missing governance artifacts are reported without command failure
- missing Git repository does not prevent status evaluation
- command performs no file writes
- service performs no file writes
- project memory is not updated at runtime
- tests cover service behavior, CLI behavior, failure behavior, and read-only behavior
- `python -m pytest` passes
- `python -m ruff check .` passes
- `python -m ruff format --check .` passes
- README instructions are accurate
- project memory and changelog are updated as implementation documentation, not runtime behavior

## Non-Goals

This Engineering Brief does not authorize:

- `forge review`
- `forge doctor`
- `forge release`
- Governance Score
- JSON output
- persisted reports
- policy packs
- project memory writes at runtime
- automatic fixes
- release approval
- changing `forge init`
- changing bootstrap templates

## Rollback Strategy

If implementation introduces unsafe behavior or scope drift:

- remove `forge status` CLI wiring from `forge/cli.py`
- remove the Status Service module if it cannot be made safe
- remove or revert status-specific tests
- revert README and changelog references to the command
- preserve CS-002.1 and DAR-CS-0001 unless the specification itself is found defective

Rollback must not modify historical ADRs, reviews, or accepted specifications unless a new review determines they are wrong.

## Verification Commands

Before claiming implementation complete, run:

```text
python -m pytest
python -m ruff check .
python -m ruff format --check .
git diff --check
```

No release tag should be created until these commands pass and documentation is updated.

## Risks

- The implementation may overreach into `forge doctor` or `forge review`.
- Output wording may imply approval or compliance too strongly.
- Read-only behavior may be weakened by future report persistence pressure.
- Git inspection may be brittle across environments.
- Status categories may become inconsistent without a small shared result structure.

## Decision

PASS.

EB-002.1 is ready to guide implementation of the read-only Governance Runtime Status Service and future `forge status` command.
