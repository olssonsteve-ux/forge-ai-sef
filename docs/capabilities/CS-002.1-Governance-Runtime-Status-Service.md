# CS-002.1 - Governance Runtime Status Service

## Status

Implementation Ready.

## Parent Capability

FCS-002 - Governance Runtime.

## Purpose

The Governance Runtime Status Service evaluates the current governance and engineering state of a Forge-governed project.

It is the first implementation-sized slice of FCS-002. It gives Forge a read-only way to answer a basic question: "What is the current governance condition of this repository?"

The service will later support the future `forge status` command, but this slice does not implement that command.

## Scope

This slice includes read-only status evaluation for a repository.

The first implementation should evaluate the presence or observable state of:

- `CONSTITUTION.md`
- `AI_ENGINEERING_CONDUCT.md`
- `PROJECT_STATE.md`
- `PROJECT_BRAIN.md`
- `AI_HANDOFF.md`
- ADR documents
- Capability Specification documents
- Capability Slice documents
- Engineering Brief documents
- test configuration
- CI configuration
- release documentation
- Git repository metadata
- Git working tree awareness

The service should provide enough information for a human or AI agent to understand whether the project has the expected Forge governance foundation.

## Non-Goals

This slice does not include:

- modifying files
- approving releases
- creating ADRs
- creating reviews
- changing project state
- updating project memory
- implementing recommendations automatically
- scoring complex code quality
- replacing human judgment
- enforcing policy by blocking normal Git or file operations
- implementing `forge review`
- implementing release automation

## Inputs

The Status Service may use:

- repository path
- project governance documents
- project memory documents
- architecture and decision documents
- capability documents
- Engineering Brief documents
- release documents
- test and CI configuration files
- Git metadata
- Forge configuration, if present
- runtime options
- optional strict mode

The initial implementation should work without a Forge configuration file when the expected repository documents are present.

## Dependencies

This slice depends on:

- `CONSTITUTION.md` as the highest governing document
- `AI_ENGINEERING_CONDUCT.md` as the AI behavior contract
- `PROJECT_STATE.md`, `PROJECT_BRAIN.md`, and `AI_HANDOFF.md` as project memory
- FCS-002 as the parent Governance Runtime specification
- ADR 0013 for the Governance Runtime capability decision
- ADR 0014 for Capability Slices in the engineering hierarchy
- the Capability Slice standard
- existing Git metadata when repository status is evaluated
- existing test and CI standards when testing and CI status are evaluated

This slice does not depend on review scoring, release automation, policy packs, or project memory mutation.

## Outputs

The Status Service should produce:

- status summary
- missing governance artifacts
- warnings
- recommendations
- readiness indicators
- category results
- human-readable output first
- machine-readable output in a future slice

The first output model should be understandable without requiring users to learn a scoring system.

## Status Model

The service should report status across these categories:

- Constitutional Status
- Governance Status
- Documentation Status
- Capability Status
- Engineering Workflow Status
- Testing Status
- Release Status
- Runtime Memory Status
- Repository Status

Each category should describe what was inspected, what result was found, and what action is recommended when action is appropriate.

## Result States

Each status item should use one of the following states:

- `OK`: the expected artifact or condition exists and appears usable.
- `WARNING`: the artifact or condition exists, but there is a concern that should be reviewed.
- `MISSING`: the expected artifact or condition was not found.
- `BLOCKED`: status evaluation could not continue for a required reason.
- `NOT_APPLICABLE`: the item does not apply to the current repository or selected runtime options.

The first implementation should avoid aggregate scores. Scores can create false confidence before the evaluation model is mature.

## Runtime Behavior

The Status Service should inspect repository files and metadata without changing them.

Expected behavior:

- Resolve the target repository path.
- Determine whether the path is readable.
- Determine whether the path appears to be a Forge-governed project.
- Inspect expected root governance files.
- Inspect `docs/decisions/` for ADR presence.
- Inspect `docs/capabilities/` for FCS and CS documents.
- Inspect `docs/engineering/` for Engineering Brief documents.
- Inspect test configuration and test directory presence.
- Inspect CI configuration presence under `.github/workflows/`.
- Inspect release documentation presence under `docs/release/`.
- Inspect Git repository availability when Git metadata is present.
- Detect whether the Git working tree has uncommitted changes when possible.
- Produce partial status when non-critical inspection fails.

The service should prefer clear findings over broad inference. A missing file should be reported as missing; it should not be interpreted as intent.

## Persistence Behavior

For the first implementation:

- no writes by default
- no automatic `PROJECT_STATE.md` updates
- no automatic `PROJECT_BRAIN.md` updates
- no automatic `AI_HANDOFF.md` updates
- no persisted report unless a future slice explicitly specifies it

Future slices may add optional report persistence after output format, ownership, and lifecycle rules are specified.

## Failure Behavior

The service should handle failure explicitly:

- Missing repository path: return invalid execution with a clear error.
- Missing Constitution: report `MISSING` for Constitutional Status, not an execution failure.
- Invalid Forge project: report blocked or incomplete status when required Forge signals are absent.
- Unreadable files: report `WARNING` or `BLOCKED` depending on whether the file is required for the selected check.
- Git unavailable: report Repository Status as partial and continue file-based evaluation.
- Git metadata missing: report Repository Status as `NOT_APPLICABLE` or `WARNING` depending on selected mode.
- Partial status possible: continue evaluating independent categories whenever safe.

Warnings should not cause command failure by themselves.

## CLI Surface

This slice defines the future command surface for:

```text
forge status
```

Initial expected behavior:

- run in the current repository by default
- optional path argument may be added later
- produce human-readable output
- perform no file writes
- use non-zero exit only for invalid execution, not for warnings or missing optional artifacts
- avoid complex scoring in the first implementation

This slice does not implement `forge status`; it only defines the bounded service that an Engineering Brief may implement.

## Acceptance Criteria

Implementation of this slice is complete when:

- Status Service can evaluate a target repository path without writing files.
- Required governance artifacts are checked for presence.
- Status categories are generated consistently.
- Missing `CONSTITUTION.md` is reported clearly.
- Missing `PROJECT_STATE.md` is reported clearly.
- Git metadata is inspected when available.
- Git absence does not prevent file-based status evaluation.
- Human-readable output explains findings and recommended next actions.
- Warnings do not produce a non-zero exit code.
- Invalid execution produces a clear error and non-zero exit code.
- No generated status text is hardcoded in templates intended for other commands.
- Tests verify the read-only behavior.
- Documentation explains the command as informational, not authoritative approval.

## Testing Expectations

Tests should cover:

- complete Forge project
- missing Constitution
- missing `PROJECT_STATE.md`
- no Git repository
- dry read-only behavior
- status category generation
- Git unavailable or unreadable metadata
- invalid repository path
- warnings that do not fail execution

The tests should prove that the service does not write to project memory or generated reports.

## Documentation Expectations

Implementation should update:

- `README.md` with the future `forge status` usage after the command exists
- `PROJECT_STATE.md` with implementation status
- `PROJECT_BRAIN.md` with durable decisions discovered during implementation
- `AI_HANDOFF.md` with handoff instructions for the Status Service
- `CHANGELOG.md` with user-visible additions
- relevant release checklist or readiness documentation if the slice is released

Documentation should avoid presenting status output as release approval.

## Constitutional Compliance

This slice supports the Constitution by making governance state visible before implementation, review, or release claims are made.

It reinforces intentional engineering by:

- surfacing missing governance artifacts
- preserving human authority over decisions
- making project memory health visible
- avoiding automatic mutation
- avoiding premature scoring
- keeping runtime behavior traceable to an accepted capability

## Relationship To Engineering Briefs

The next Engineering Brief for Governance Runtime should implement only this slice.

That Engineering Brief should define:

- module boundaries
- command wiring
- output formatting
- test plan
- error handling details
- exact file inspection rules
- whether any internal service object is introduced

The brief must not expand into review scoring, release approval, policy packs, or memory mutation.

## Release Readiness Criteria

This slice is ready for release when:

- implementation remains limited to read-only status evaluation
- tests pass locally and in CI
- lint and format checks pass
- `forge status` behavior matches this slice and its Engineering Brief
- README usage is accurate
- project memory is updated
- changelog records the addition
- no automatic file mutation is introduced
- release documentation identifies known limitations

## Risks

- Over-scoring too early could create false confidence.
- Status language may be interpreted as approval instead of information.
- Too much complexity could make the first Governance Runtime service hard to trust.
- Accidental writes would violate the read-only boundary.
- Git inspection may behave differently across environments.
- Missing artifacts may be normal for non-Forge repositories.
- Recommendations may drift into automated design judgment too soon.
