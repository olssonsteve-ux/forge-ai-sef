# CS-002.2 - Governance Runtime Version Consistency Check

## Status

Closed.

## Parent Capability

FCS-002 - Governance Runtime.

## Purpose

The Governance Runtime Version Consistency Check defines a read-only service that validates version consistency across a Forge repository.

This service extends the Status Service introduced by CS-002.1. Its purpose is to detect inconsistent version information before releases and during project reviews.

The slice exists because PRR-0001 found that Forge `v0.4.0` was released while active documentation still referenced Forge `0.3.3`.

## Scope

This slice verifies consistency between version information stored in repository artifacts.

Version sources may include:

- Git tags
- `README.md`
- `CHANGELOG.md`
- `PROJECT_STATE.md`
- `AI_HANDOFF.md`
- `pyproject.toml`, if present
- release documentation
- repository metadata

The check should detect whether release-facing documents agree on the current project version or release tag.

## Non-Goals

This slice does not include:

- modifying files
- rewriting documentation
- creating commits
- creating Git tags
- automatically resolving inconsistencies
- inferring missing versions as facts
- approving releases
- publishing packages
- changing project memory
- adding a new CLI command

The service only detects and reports.

## Inputs

The Version Consistency Check may use:

- repository path
- Git metadata
- repository documentation
- package metadata, if present
- release documentation
- optional strict mode in a future slice or brief

This slice depends on:

- `CONSTITUTION.md` as the highest governing document

## Outputs

The service should produce:

- version consistency report
- detected inconsistencies
- warnings
- recommendations
- readiness indicator
- future machine-readable output, out of scope for the first implementation

The output must remain informational. It must not claim release approval.

## Version Model

The check should distinguish these version concepts:

### Current Development Version

The version recorded in active project state or package metadata for ongoing development.

Potential sources:

- `PROJECT_STATE.md`
- `pyproject.toml`
- README current state

### Latest Release Tag

The most recent Git tag that represents a Forge release.

Potential sources:

- local Git tags
- remote Git tags when available in a future extension

The first implementation should avoid network dependency.

### Repository Documentation Version

The release or version identity described in active documentation.

Potential sources:

- `README.md`
- `CHANGELOG.md`
- `AI_HANDOFF.md`
- release checklist documents

### Working Tree State

The current Git working tree condition.

The check should report whether uncommitted changes may make version consistency results provisional.

### Supported Version Sources

The first implementation should support:

- Git tag metadata when present
- `README.md`
- `CHANGELOG.md`
- `PROJECT_STATE.md`
- `AI_HANDOFF.md`
- `pyproject.toml` when present
- `docs/release/` when present

The implementation should report missing sources as findings, not infer their intended values.

## Result States

Use the Governance Runtime result states:

- `OK`
- `WARNING`
- `MISSING`
- `BLOCKED`
- `NOT_APPLICABLE`

Suggested interpretation:

- `OK`: available version sources agree.
- `WARNING`: sources exist but contain conflicting or suspicious version references.
- `MISSING`: an expected source is absent.
- `BLOCKED`: the check cannot safely evaluate required evidence.
- `NOT_APPLICABLE`: the source does not apply to this repository or selected mode.

## Runtime Behavior

The service should inspect version-bearing artifacts without changing them.

Expected behavior:

- Resolve the target repository path.
- Inspect local Git tags when Git metadata is available.
- Identify the latest release tag using the accepted Forge tag pattern.
- Inspect release-facing documentation for version references.
- Compare active documentation references with the latest release tag or selected target version.
- Report mismatches with evidence and file names.
- Report partial results when Git or optional files are unavailable.
- Avoid network calls in the first implementation.

The check should not treat every historical version reference as an error. Historical changelog sections, old release checklists, prior DARs, and post-release reviews may correctly mention older versions.

## Persistence Behavior

The first implementation must not persist reports and must not update files.

Future persistence requires a separate Capability Slice and Engineering Brief.

## Failure Behavior

The service should handle failures explicitly:

- Missing Git: return a warning or `NOT_APPLICABLE` repository item and continue document inspection.
- Missing `README.md`: report `MISSING`.
- Missing `CHANGELOG.md`: report `MISSING`.
- Missing `PROJECT_STATE.md`: report `MISSING`.
- Missing `AI_HANDOFF.md`: report `MISSING`.
- Missing `pyproject.toml`: report `NOT_APPLICABLE` unless package metadata is required by selected mode.
- Missing release documentation: report `MISSING` or `NOT_APPLICABLE` depending on the repository maturity.
- Invalid repository: return `BLOCKED` or invalid execution according to the Status Service rules.
- Unreadable files: report `WARNING` or `BLOCKED` depending on whether the file is required.
- Partial results: allowed when independent evidence can still be evaluated.

## CLI Behavior

This slice extends:

```text
forge status
```

Do not introduce a new CLI command.

Version consistency should become one Status category or a clearly grouped set of Status items inside the existing status output.

The command must remain read-only.

## Acceptance Criteria

This slice is implementation-ready when:

- version sources are defined
- release tag selection rules are defined
- historical version reference handling is defined
- active documentation version expectations are defined
- failure behavior is defined
- test cases are defined
- output remains informational
- no runtime mutation is allowed
- the check integrates into `forge status`
- the check does not introduce scoring or release approval

Implementation is complete when:

- `forge status` reports version consistency as a status category or item group
- matching active versions report `OK`
- missing required sources report `MISSING`
- version mismatches report `WARNING`
- missing Git metadata does not block document checks
- dirty working tree state is reported clearly
- tests cover matching, missing, mismatched, clean, and dirty repository cases
- no files are modified at runtime

## Testing Expectations

Tests should cover:

- matching versions
- missing `README.md`
- missing `CHANGELOG.md`
- missing Git tag
- multiple version mismatches
- clean repository
- dirty repository
- missing `pyproject.toml`
- historical changelog versions that should not fail active consistency
- read-only behavior

## Documentation Expectations

Implementation should update:

- `README.md` with the expanded `forge status` behavior
- `PROJECT_STATE.md` with implementation status
- `PROJECT_BRAIN.md` with durable version consistency decisions
- `AI_HANDOFF.md` with future-agent guidance
- `CHANGELOG.md` with the new Governance Runtime check
- release documentation if release checks are affected

Documentation must state that the check detects version drift and does not fix it automatically.

## Constitutional Compliance

This slice supports:

- Engineering discipline by making release identity explicit and verifiable.
- Review before release by detecting version drift before release decisions are made.
- Governance by connecting Git tags, project memory, documentation, and release records.
- Trustworthy software by reducing confusion about what version has actually been released.

The slice preserves human authority because it reports findings and recommendations without making release decisions or modifying files.

## Relationship To Status Service

CS-002.2 extends CS-002.1.

It should reuse the Status Service result model and appear in `forge status`. It must not create a separate command or weaken the read-only boundary.

## Relationship To Engineering Briefs

The next Engineering Brief for this slice should implement only read-only version consistency checks inside `forge status`.

That brief should define:

- exact version parsing rules
- active versus historical version reference rules
- latest release tag selection rules
- package metadata handling
- dirty working tree messaging
- output wording
- tests and fixtures

The brief must not add automatic fixes, tag creation, changelog rewrites, release approval, CI enforcement, or project memory mutation.

## Relationship To Future Release Service

A future Release Service may use version consistency findings as release-readiness evidence.

This slice does not approve releases and does not block releases by itself.

## Relationship To Future Review Service

A future Review Service may cite version consistency findings during release, documentation, or project health reviews.

This slice provides evidence; it does not replace review judgment.

## Relationship To Future Planning Service

A future Planning Service may recommend version cleanup work when this check reports drift.

This slice does not prioritize or schedule remediation automatically.

## Release Readiness Criteria

This slice is ready for release when:

- implementation remains read-only
- `forge status` reports version consistency without adding a new command
- matching active versions report `OK`
- mismatched active versions report `WARNING`
- missing required version sources report `MISSING`
- missing Git metadata does not block document-based checks
- historical version references are not treated as active mismatches
- tests prove read-only behavior
- README and project memory describe the behavior accurately
- no release approval, scoring, or automatic remediation is introduced

## Risks

- False positives from historical version references.
- Version parsing may become brittle across documentation styles.
- Future release models may support multiple active versions.
- Package metadata may not always match release tags before package publishing is adopted.
- Dirty working trees can make status results provisional.
- Overly strict checks may create release friction without improving trust.
