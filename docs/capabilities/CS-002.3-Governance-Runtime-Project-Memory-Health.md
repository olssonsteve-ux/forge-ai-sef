## Parent Capability

FCS-002 - Governance Runtime.

## 1. Purpose

Project Memory Health defines a read-only Governance Runtime increment that evaluates whether the
active project-memory artifacts in a Forge-governed repository are present, structurally valid,
mutually coherent, and current enough for human and AI contributors to rely upon.

The slice extends the existing `forge status` service with one human-readable status category or
item group. It does not create a new command, score project memory, modify files, or approve work.

## 2. Product Owner Selection

The Product Owner selects Project Memory Health as the next Governance Runtime Capability Slice.

The alternatives were evaluated as follows:

| Alternative | Direct value | FCS-002 alignment | Dependency and size | Read-only and deterministic fit | Prematurity or scope risk | Decision |
| --- | --- | --- | --- | --- | --- | --- |
| Shared Governance Runtime result model | Low user-visible value | Supporting only | Current `StatusState`, `StatusItem`, `StatusCategory`, and `StatusReport` already suffice | Feasible | High risk of abstraction before a second concrete need | Not selected as a prerequisite |
| JSON output for `forge status` | Presentation value | Allowed future output | Requires a stable machine-readable schema | Read-only and deterministic | Does not strengthen governance evidence by itself | Deferred |
| Persisted status reports | Moderate audit value | Future persistence surface | Requires ownership, path, overwrite, retention, and lifecycle contracts | Not read-only | Premature persistence and mutation risk | Deferred |
| Release readiness evaluation | High eventual value | Strong FCS-002 alignment | Depends on broader reviewed evidence and Release Authority boundaries | Can be read-only | High false-authority and premature-gating risk | Deferred |
| Project Memory Health | High daily human and AI value | Directly named by FCS-002 | Bounded extension of existing status service | Strong read-only and deterministic fit | False positives controllable through active-section rules | Selected |
| Further Version Consistency enhancement | Incremental value | Aligned but already served by CS-002.2 | Would require a new concrete defect | Read-only | Risks duplicating the closed version slice | Not selected |

Project Memory Health strengthens real governance rather than presentation. It detects when the
repository-local operational context that contributors are required to trust is missing, malformed,
contradictory, or demonstrably stale.

## 3. Problem Statement

Forge requires contributors to read `PROJECT_STATE.md`, `PROJECT_BRAIN.md`, and `AI_HANDOFF.md`
before meaningful work. Presence checks alone cannot establish that those artifacts are usable.

Concrete failure modes include:

- one or more required project-memory files are missing
- a memory file is empty or lacks a contract-required section
- current status or objective sections contain no usable content
- Project State and AI Handoff name different active work without explaining the transition
- AI Handoff recommends a gate that an authoritative artifact proves has already passed
- a closed artifact is still presented as pending or implementation-ready in active memory
- an active artifact reference cannot be resolved locally
- Project Brain presents a rejected, superseded, or deprecated ADR as a current decision
- active release lifecycle labels disagree with the applicable release record
- historical context is incorrectly interpreted as current work

These failures weaken handoff quality and can cause humans or AI agents to repeat completed work,
skip required gates, act under stale permissions, or mistake historical context for current truth.

## 4. Intended Outcome

`forge status` can report a `Project Memory Health` category that:

- confirms required memory files and sections exist
- identifies missing or empty required evidence
- checks explicit active-work and next-step coherence conservatively
- validates resolvable active artifact references
- detects explicit lifecycle or release-state contradictions supported by authoritative local records
- distinguishes active content from historical content
- provides concise evidence and advisory next actions
- remains informational, local, deterministic, and read-only

The outcome is greater confidence that project memory is safe to use as operational context. It is
not certification that all documentation is correct or well written.

## 5. Scope

This slice includes:

- one new Project Memory Health category or clearly grouped item set in existing `forge status`
- deterministic inspection of the three mandatory project-memory files
- contract-required heading and non-empty-section checks
- conservative active-work, handoff, lifecycle, release-state, and reference-integrity checks
- human-readable findings using the existing Governance Runtime status vocabulary
- advisory remediation guidance
- focused fixtures and read-only regression tests
- coexistence with Version Consistency Status

The slice evaluates project memory, not the repository in general. Supporting artifacts may be read
only to verify an explicit claim made in an active project-memory section.

## 6. Explicit Exclusions

This slice does not include:

- semantic scoring of writing quality, completeness, tone, or usefulness
- LLM-based interpretation or probabilistic inference
- automatic edits, memory synchronization, or generated repair patches
- changing lifecycle state or accepting a review
- report persistence or status history
- JSON or other machine-readable output
- a new CLI command or option
- aggregate scores, thresholds, certification, or release blocking
- release approval or Release Candidate authorization
- policy packs or configurable rule engines
- remote repository, remote Git, or network inspection
- historical-document cleanup
- generalized cross-document consistency checking outside project memory
- reimplementation of CS-002.2 version consistency
- broad validation of every ADR, Capability Slice, Engineering Brief, review, or release record
- a plugin system, parser framework, or generalized governance query engine

## 9. Outputs

The slice extends existing `forge status` output with:

```text
Project Memory Health: <STATE>
  <bounded category summary>
  - <check label>: <STATE> - <evidence-based message>
```

Each finding must include:

- the file and active section inspected
- the observed fact or explicit contradiction
- the local authoritative artifact used, when applicable
- an advisory next action when action is justified

The output remains informational and must repeat no release-approval or certification language.

## 10. Evaluation Rules

### Rule 1 - Required File Presence

- Input: the three mandatory root paths.
- Authoritative scope: repository root; no Markdown section is required for this file-level check.
- Rule: each path must be a readable regular file.
- Result: `OK` when present and readable; `MISSING` when absent; `BLOCKED` when present but unreadable.
- Evidence: exact relative path.
- False-positive control: do not require optional supporting artifacts.
- Exclusion: do not infer why a file is absent.
- Failure behavior: an I/O or UTF-8 decoding failure is `BLOCKED` for checks dependent on that file;
  independent files continue.

### Rule 2 - Required Section Presence

- Input: exact second-level Markdown headings required by each governing schema.
- Authoritative sections: all required sections enumerated in Section 8 for the applicable file.
- Rule: every required heading must occur exactly once and contain non-whitespace content before the
  next second-level heading.
- Result: `OK` when complete; `MISSING` for an absent or empty required section; `WARNING` for a
  duplicated required heading.
- Evidence: file and heading.
- False-positive control: heading order and prose style are not evaluated in this slice.
- Exclusion: optional headings are not required.
- Failure behavior: unreadable or non-UTF-8 input is `BLOCKED`; malformed heading syntax that does
  not form an exact second-level required heading is treated as `MISSING`, not guessed.

### Rule 3 - Current Status And Objective Content

- Input: Project State `Status` and `Current Objective`, plus AI Handoff `Immediate Next Step`.
- Authoritative sections: exactly those three named active sections.
- Rule: each section must contain at least one non-heading, non-comment content line after Markdown
  whitespace is removed.
- Result: `OK` when usable content exists; `MISSING` when empty.
- Evidence: file and section only; do not echo sensitive or unbounded content.
- False-positive control: no judgment of writing quality or strategic merit.
- Exclusion: length, grammar, and tone are not evaluated.
- Failure behavior: a missing section follows Rule 2; unreadable input is `BLOCKED`; unsupported
  Markdown content is not semantically interpreted.

### Rule 4 - Active Artifact Reference Integrity

- Input: explicit identifiers in Project State `Status`, `Current Objective`, and `Next Recommended
  Work`, and AI Handoff `Current Repository State` and `Immediate Next Step`.
- Authoritative sections: exactly the five active sections named in the input.
- Rule: identifiers must match one of these case-sensitive forms and deterministic path prefixes:
  `ADR NNNN` or `ADR-NNNN` -> `docs/decisions/NNNN-`; `FCS-NNN` ->
  `docs/capabilities/FCS-NNN-`; `CS-NNN.S` -> `docs/capabilities/CS-NNN.S-`; `EB-NNN` or
  `EB-NNN.S` -> `docs/engineering/EB-NNN-` or `docs/engineering/EB-NNN.S-`; `DAR-CS-NNNN`,
  `DAR-EB-NNNN`, or `DAR-AR-NNNN` -> the identical prefix under `docs/reviews/`; and `PRR-NNNN` ->
  `docs/reviews/PRR-NNNN-`. Resolution is prefix-based within that one governed directory and must
  yield exactly one Markdown file. No substring, edit-distance, case-folded, or repository-wide
  matching is permitted. Full 40-character hexadecimal Git commit hashes must resolve locally when
  Git metadata is available.
- Result: `OK` for one match; `MISSING` for no match; `WARNING` for an ambiguous match;
  `NOT_APPLICABLE` for commit checks without Git.
- Evidence: identifier and resolved path or missing/ambiguous candidates.
- False-positive control: do not treat ordinary numbers, versions, filenames without governed
  identifiers, or references in historical sections as active artifacts.
- Exclusion: do not validate the complete contents of the referenced artifact.
- Failure behavior: an unreadable governed directory or I/O error is `BLOCKED`; a missing directory
  or zero prefix matches is `MISSING`; multiple prefix matches are `WARNING`; Git absence makes only
  the commit-reference sub-check `NOT_APPLICABLE`.

### Rule 5 - Active Objective And Handoff Coherence

- Input: governed work identifiers extracted under Rule 4 from Project State `Current Objective`
  and `Next Recommended Work`, and AI Handoff `Immediate Next Step`.
- Authoritative sections: Project State `Current Objective`, only the first non-empty list item in
  `Next Recommended Work`, and AI Handoff `Immediate Next Step`.
- Rule: when both sides name work identifiers, AI Handoff must name at least one identifier present
  in the Project State active objective or first recommended work item. Disjoint explicit work sets
  are contradictory. When either side names no governed identifier, the check is `NOT_APPLICABLE`.
- Result: `OK`, `WARNING`, or `NOT_APPLICABLE`.
- Evidence: the two identifier sets and section names.
- False-positive control: compare identifiers, not free-form semantic similarity.
- Exclusion: do not decide whether the selected work itself is strategically correct.
- Failure behavior: a missing required section follows Rule 2; unresolved references follow Rule 4;
  when either side has no valid governed work identifier, return `NOT_APPLICABLE` rather than infer
  meaning from prose.

### Rule 6 - Explicit Lifecycle Claim Coherence

- Input: explicit artifact identifier and lifecycle label pairs in the active sections defined by
  Rule 4.
- Authoritative sections: the Rule 4 active sections and the resolved artifact's explicit top-level
  `Status:` field or `## Status` section; for a review, its explicit final result is also authoritative.
- Rule: parse only labels defined by the Lifecycle Standard or the artifact-local lifecycle when
  they occur in the same sentence or list item as an identifier. Normalization may strip Markdown
  backticks, trim whitespace and terminal punctuation, collapse internal whitespace, and compare
  ASCII case-insensitively. No synonym expansion is permitted. Only mappings explicitly stated by
  the Lifecycle Standard, such as ADR `Accepted` to common `Approved`, may be applied. A different
  authoritative status is a contradiction.
- Result: `OK` when equal; `WARNING` when contradictory; `NOT_APPLICABLE` when no parseable explicit
  claim exists; `MISSING` when the artifact cannot be resolved.
- Evidence: memory claim, authoritative status, and artifact path.
- False-positive control: no inferred synonym mapping beyond mappings explicitly defined by the
  Lifecycle Standard.
- Exclusion: do not derive lifecycle state from prose lacking an explicit governed label.
- Failure behavior: missing artifact is `MISSING`; unreadable status evidence is `BLOCKED`; absent or
  unsupported labels are `NOT_APPLICABLE`; multiple conflicting authoritative status fields are
  `WARNING` and must not be resolved by guesswork.

### Rule 7 - Handoff Gate Staleness

- Input: AI Handoff `Immediate Next Step` statements containing an explicit work identifier and one
  of the bounded gate phrases `pending review`, `awaiting review`, `ready to commit`, `commit
  pending`, or `implementation ready`.
- Authoritative section: AI Handoff `Immediate Next Step`; proving evidence is limited to the named
  artifact, its explicitly linked review, and its recorded full implementation commit.
- Rule: `pending review` or `awaiting review` is stale only when the linked review has an explicit
  final `PASS`; `ready to commit` or `commit pending` is stale only when a recorded full commit hash
  resolves locally; `implementation ready` is stale only when the named artifact explicitly records
  `Implemented`, `Implementation Reviewed`, or `Closed`. No other gate phrase or inferred evidence
  is evaluated.
- Result: `OK`, `WARNING`, `MISSING`, or `NOT_APPLICABLE`.
- Evidence: gate phrase and proving artifact, review, or commit.
- False-positive control: require both an explicit identifier and a bounded gate phrase.
- Exclusion: do not infer staleness from dates, wording style, or absence of recent edits.
- Failure behavior: unresolved proving artifact follows Rule 4; unreadable evidence is `BLOCKED`;
  absent positive proof returns `OK` for a legitimately pending recognized gate, not `WARNING`.

### Rule 8 - Active Release Lifecycle Coherence

- Input: explicit release identifier and lifecycle label in Project State `Planned Release`, AI
  Handoff `Current Repository State`, and the matching active `docs/release/checklist-X.Y.Z.md`.
- Authoritative sections: Project State `Planned Release`, AI Handoff `Current Repository State`,
  and the matching checklist's top-level `Status:` field.
- Rule: when the same release identifier is present in more than one input, explicit release
  lifecycle labels must agree with the checklist `Status`. Disagreement in numeric version identity
  is left to Version Consistency Status.
- Result: `OK`, `WARNING`, `MISSING`, or `NOT_APPLICABLE`.
- Evidence: release identifier, labels, and checklist path.
- False-positive control: compare only explicit labels for the same release identifier.
- Exclusion: do not decide release readiness or block a release.
- Failure behavior: no shared release identifier is `NOT_APPLICABLE`; a named missing checklist is
  `MISSING`; unreadable or multiply defined checklist status is `BLOCKED`; explicit disagreement is
  `WARNING`.

### Rule 9 - Current Decision Authority

- Input: ADR identifiers explicitly listed in Project Brain `Current Decisions`.
- Authoritative sections: Project Brain `Current Decisions` and the resolved ADR's explicit status.
- Rule: resolve each ADR and read its explicit ADR status. `Rejected`, `Superseded`, or `Deprecated`
  ADRs must not be presented as current authority. Retention is accepted as historical only when the
  same list item contains the exact qualifier `historical`, `rejected`, `deprecated`, or
  `superseded by ADR NNNN`/`superseded by ADR-NNNN`; the replacement identifier must resolve under
  Rule 4. No inferred supersession or free-form synonym qualifies.
- Result: `OK`, `WARNING`, or `MISSING`.
- Evidence: Project Brain item, ADR status, and path.
- False-positive control: evaluate only ADRs explicitly named in `Current Decisions`.
- Exclusion: do not judge decisions that lack an ADR reference or scan historical narrative.
- Failure behavior: missing ADR or replacement is `MISSING`; unreadable ADR status is `BLOCKED`;
  ambiguous resolution is `WARNING`; a supported historical qualifier with valid evidence is `OK`.

### Candidate Checks Deferred Or Rejected

- Exhaustive detection that Project State omitted every committed or closed artifact: deferred
  because it requires a completeness registry beyond project-memory scope.
- Semantic equivalence of free-form objectives and next steps: rejected as non-deterministic.
- Writing-quality, specificity, or usefulness scores: rejected.
- Modification-time freshness thresholds: rejected.
- General consistency across README, changelog, all ADRs, reviews, briefs, and releases: rejected.
- Automatic repair text or patches: rejected.

## 11. Status Semantics

This slice reuses the existing states without adding or renaming values:

- `OK`: the bounded check completed and found coherent evidence.
- `WARNING`: evidence exists but contains a contradiction, duplicate, ambiguity, or proven stale
  active claim requiring human review.
- `MISSING`: a required file, required section, or explicitly referenced active artifact is absent.
- `BLOCKED`: a required existing file cannot be read or safely parsed enough to continue that check.
- `NOT_APPLICABLE`: the repository lacks Forge signals or the specific check has no eligible explicit
  claim or required optional context.

Category rollup must use the existing deterministic precedence:

1. any `BLOCKED` item -> category `BLOCKED`
2. otherwise any `MISSING` item -> category `MISSING`
3. otherwise any `WARNING` item -> category `WARNING`
4. all items `NOT_APPLICABLE` -> category `NOT_APPLICABLE`
5. otherwise -> category `OK`, including a mixture of `OK` and `NOT_APPLICABLE`

`OK` means only that the bounded rules found no issue; it does not certify overall correctness,
quality, lifecycle approval, or release readiness. Findings do not change CLI exit behavior:
successful evaluation returns the existing success code even when warnings or missing items are
reported.

## 12. Architecture Boundaries

The existing Status Service already provides the required result and composition model:

- `StatusState`
- `StatusItem`
- `StatusCategory`
- `StatusReport`
- category rollup
- Markdown section extraction
- local Git read-only inspection

A separate Shared Governance Runtime Result Model slice is not a prerequisite.

The module boundary is:

- introduce one private `forge/project_memory.py` helper module for UTF-8 document loading,
  exact second-level section extraction, bounded identifier and lifecycle-claim parsing, and
  deterministic reference resolution
- keep `StatusState`, `StatusItem`, `StatusCategory`, `StatusReport`, category aggregation, Project
  Memory Health rule evaluation, and CLI-facing composition in `forge/status.py`
- keep `forge/cli.py` unchanged unless an implementation defect proves otherwise

The helper module must return parsed facts and resolution evidence, not status categories, scores,
recommendations, or CLI text. It must remain private, project-memory-specific, local, deterministic,
and read-only. It must not move existing status types or introduce a generalized result framework,
plugin system, policy engine, parser framework, registry, or public API.

## 14. Persistence And Read-Only Guarantees

The implementation must:

- read local repository files only
- use local Git only for an explicit commit-reference check and existing repository context
- make no network calls
- write no files or directories
- update no project-memory documents at runtime
- persist no report
- stage, commit, tag, or mutate no Git state
- create no ADR, review, issue, or lifecycle record
- change no lifecycle or release state
- make no authoritative repair

Remediation text may recommend a human review of a named file or section. It must remain advisory
and must not present suggested wording as an accepted project fact.

## 15. Failure Behavior

- Invalid or unreadable target directory: preserve existing `StatusServiceError` behavior.
- Non-Forge repository: Project Memory Health is `NOT_APPLICABLE`; evaluation of other categories
  continues.
- Missing mandatory memory file in a Forge-signaled repository: report `MISSING` and continue
  independent checks.
- Unreadable mandatory file: report `BLOCKED` for dependent checks and continue independent files.
- Malformed or duplicate headings: report the rule-specific finding without rewriting the file.
- Missing supporting artifact named by an active claim: report `MISSING` for that reference.
- Ambiguous identifier resolution: report `WARNING` with candidate paths.
- Git unavailable: file-based checks continue; explicit commit checks are `NOT_APPLICABLE`.
- Unsupported or ambiguous prose: report `NOT_APPLICABLE`, not a guessed contradiction.
- Unexpected internal error: preserve existing invalid-execution handling and human-readable error.

## 20. Risks And False-Positive Controls

### Free-Form Language

Risk: objectives and lifecycle statements use varied prose.

Control: evaluate only exact active sections, governed identifiers, governed lifecycle labels, and
bounded gate phrases. Unsupported prose is `NOT_APPLICABLE`.

### Historical Context

Risk: valid historical decisions and completed gates are flagged as stale.

Control: ignore content outside schema-defined active sections unless an active section explicitly
references it as current evidence.

### General Consistency Creep

Risk: the slice becomes a repository-wide document-consistency engine.

Control: supporting artifacts are opened only to validate explicit active memory claims.

### False Authority

Risk: health output is interpreted as certification or approval.

Control: use existing informational states, cite bounded evidence, preserve successful command
execution for findings, and prohibit release or lifecycle decisions.

### Parser Growth

Risk: many file-specific rules make `forge/status.py` difficult to maintain.

Control: use the DAR-approved private `forge/project_memory.py` boundary for parsing and resolution;
prohibit generalized parser or policy frameworks.
