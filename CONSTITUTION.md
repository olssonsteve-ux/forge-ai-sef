# Forge Constitution

> Build software with intention.

## Preamble

Forge exists because software built with humans and AI must remain understandable, governable, and maintainable over time.

Forge is an AI-Native Software Engineering Platform.

Forge provides a disciplined engineering environment where humans and AI collaborate to design, build, review, govern and evolve software.

The Constitution is the highest governing document in Forge. It defines the permanent identity, principles, governance model, and decision framework from which every future strategy, roadmap, capability, brief, implementation, review, and release shall derive.

## Motto

Build software with intention.

This motto means:

- Engineering work should begin with purpose, constraints, and expected behavior.
- Architecture should make future change safer, not merely make current implementation possible.
- Human-AI collaboration should amplify judgment instead of hiding responsibility.
- Software quality should be designed into the system rather than inspected in at the end.
- Product development should connect decisions to durable user and maintainer value.

## Official Identity

Forge is an AI-Native Software Engineering Platform.

Forge is a platform because it provides the operating foundation for repeated engineering work: governance, memory, specifications, standards, templates, quality gates, reviews, and release discipline.

Forge is not merely a framework because its purpose is broader than reusable code contracts. Forge governs how software projects are conceived, described, built, reviewed, and evolved.

Forge is not merely a toolkit because its tools derive from a coherent engineering model rather than existing as independent utilities.

Forge is not merely an engineering system because it is intended to be extended, reused, and operated as a durable product foundation across many projects.

## Vision

Forge will enable trustworthy human-AI software engineering at long horizons.

Forge should help people and AI agents collaborate with shared context, explicit decisions, disciplined review, and durable knowledge. It should make software easier to understand, safer to change, clearer to govern, and more resilient across time.

Forge should preserve engineering intent so that future contributors can understand not only what exists, but why it exists, what tradeoffs shaped it, and what must remain true as it evolves.

## Mission

Forge exists to help humans and AI design, review, build, govern, maintain, and evolve software together.

Forge enables this by:

- making project intent explicit before implementation
- turning capabilities into specifications before features become code
- preserving project memory in the repository
- making architecture decisions reviewable
- defining standards that guide implementation
- establishing quality gates before release
- creating handoff context for future contributors
- improving the engineering system through deliberate review

## Core Principles

### Architecture Before Implementation

Purpose: establish structure, boundaries, and tradeoffs before code hardens them.

Engineering rationale: implementation without architecture tends to encode accidental decisions.

Long-term value: future changes remain explainable and less costly.

### Specifications Before Code

Purpose: define expected behavior before automation exists.

Engineering rationale: specifications reduce ambiguity and make verification possible.

Long-term value: capabilities can evolve without losing their original intent.

### Capabilities Before Features

Purpose: build durable engineering abilities rather than isolated feature increments.

Engineering rationale: capabilities describe what Forge can reliably do across workflows.

Long-term value: the platform grows coherently instead of accumulating disconnected commands.

### Review Before Release

Purpose: ensure that changes meet architectural, quality, documentation, and governance expectations.

Engineering rationale: release is a trust event, not only a Git event.

Long-term value: users and maintainers can rely on Forge's evolution.

### Documentation Before Optimization

Purpose: make the system understandable before making it faster or more elaborate.

Engineering rationale: undocumented optimization often obscures behavior and tradeoffs.

Long-term value: performance work remains accountable to maintainability.

### Engineering Discipline Over Engineering Speed

Purpose: prefer durable progress over fragile acceleration.

Engineering rationale: speed that damages comprehension creates downstream cost.

Long-term value: Forge remains safe to extend as its surface area grows.

### Explicit Behavior Over Hidden Behavior

Purpose: make generated output, automation, and decisions visible.

Engineering rationale: hidden behavior is difficult to review, test, or govern.

Long-term value: human maintainers remain in control.

### Deterministic Engineering Whenever Possible

Purpose: prefer repeatable behavior, stable outputs, and clear inputs.

Engineering rationale: deterministic workflows are easier to test, audit, and hand off.

Long-term value: human-AI collaboration becomes more predictable and trustworthy.

### Human Authority With AI Leverage

Purpose: use AI to extend engineering capability without removing accountability.

Engineering rationale: AI can draft, inspect, and accelerate, but durable decisions require explainable authority.

Long-term value: Forge supports collaboration without surrendering governance.

## Product Philosophy

Forge develops Forge because the platform must prove its own engineering model before asking other projects to trust it.

Every capability begins with a specification because capability behavior must be understandable, reviewable, and testable before implementation.

Design Authority Reviews exist because architecture quality decays when change is accepted without deliberate inspection.

Governance is engineering because rules, standards, release gates, and decision authority directly shape system behavior.

Documentation is part of the product because it carries intent, contracts, and memory for humans and AI agents.

Software quality is an architectural property because maintainability, testability, reliability, and evolvability are shaped by structure and decisions before they are measured by tools.

## Constitutional Governance

Forge governance follows this hierarchy:

```text
Constitution
  |
  v
Product Strategy
  |
  v
Roadmap
  |
  v
Capability Specifications
  |
  v
Engineering Briefs
  |
  v
Implementation
  |
  v
Testing
  |
  v
Design Authority Review
  |
  v
Release
```

The Constitution defines identity, principles, governance, and decision rules.

Product Strategy interprets the Constitution into product direction.

The Roadmap orders strategic work into coherent milestones.

Capability Specifications define permanent platform capabilities before implementation.

Engineering Briefs define bounded engineering work within accepted capabilities or platform needs.

Implementation turns accepted specifications and briefs into working behavior.

Testing verifies behavior against the accepted contract.

Design Authority Review evaluates architecture, maintainability, quality, governance, and readiness.

Release publishes only work that has satisfied the applicable gates.

## Governance Responsibilities

The Product Owner protects product direction, user value, and roadmap coherence.

The Chief Architect protects constitutional alignment, architecture quality, and long-term coherence.

The Implementation Agent builds only within accepted specifications, briefs, and standards.

The Review Authority evaluates changes before release and records findings.

The Quality Authority protects testing, code quality, documentation quality, and release readiness.

The Release Authority confirms that the release satisfies its gates and records the release decision.

One contributor may hold multiple responsibilities, but the responsibilities must remain distinct.

## Decision Framework

When multiple engineering solutions exist, Forge prefers:

- readability over cleverness
- architectural clarity over incidental convenience
- explicit behavior over hidden behavior
- documentation over assumed knowledge
- maintainability over short-term speed
- backward compatibility when it protects users and generated projects
- testability over unverified behavior
- predictability over surprising automation
- engineering sustainability over local optimization

Tradeoffs are allowed, but they must be explainable.

## Amendment Rule

The Constitution may be extended when Forge learns durable lessons.

It should almost never be replaced.

Any amendment must:

- preserve the motto and constitutional hierarchy unless a Design Authority Review approves otherwise
- explain why the existing Constitution is insufficient
- include an ADR
- update all affected authority documents
- pass constitutional review before release
